블로그 대표이미지 만드는 일을 Codex CLI에 맡긴 이야기 — fallback 사다리는 그대로 두고

이 글의 원본은 Tistory 블로그에서 확인할 수 있습니다.
**OpenOrchestrator 시리즈 8편** | 2026.05

>

이 글을 읽으면 세 가지를 알게 됩니다:
- 자동화 파이프라인에 새 단계를 끼워 넣을 때 기존 동작을 어떻게 보존하는지
- Windows에서 만난 의외의 함정 하나와 그 우회 방법
- 운영 중에 새 단계를 즉시 끄는 비상정지 스위치를 어떻게 1줄로 만들었는지

7편을 발행하고 나서 또렷해진 한 자리

지난 7편에서 Tistory 글을 GitHub Pages 미러와 IndexNow로 검색엔진에 자동으로 알리는 구조를 정리했습니다. 그래서 발행 파이프라인은 거의 모든 단계가 사람 손을 떠나 있습니다.

- 글은 자동으로 작성됩니다

- 카테고리는 자동으로 붙습니다

- 비공개 임시저장도 자동입니다

- 검토 후 공개 발행 버튼은 사람이 한 번 누릅니다

- 발행 직후 검색엔진 알림도 자동입니다

그런데 이 흐름을 7편까지 굴려 보고 나서 한 자리가 늘 어색하다는 게 또렷해졌습니다 — 대표이미지(썸네일).

기존에 모든 글에 붙던 자동 썸네일은 모두 같은 패턴이었습니다. 보라/파랑 그라데이션 배경에 글 제목을 ASCII(영문자만 표현하는 텍스트 포맷)로 바꿔 박은 단조로운 자리표시자. 사진관에서 사진을 안 찍었을 때 액자에 들어가는 "샘플 사진"을 매번 그대로 노출하고 있는 것과 비슷한 느낌이었습니다.

이번 글은 그 한 자리를 어떻게 정리했는지에 대한 기록입니다.

fallback 사다리만 있던 시절

기존 썸네일 모듈은 세 가지 방법을 순서대로 시도하게 돼 있었습니다.

| 순서 | 방법 | 실제 동작 |

|---|---|---|

| 1 | 내부 이미지 생성 API (로컬 서버) | 거의 항상 꺼져 있음 |

| 2 | OpenAI 이미지 직접 호출 (유료 옵션) | 옵션 플래그를 켜야 동작 |

| 3 | PIL(Python에서 그림을 그릴 때 쓰는 라이브러리)로 그라데이션 + 텍스트 박스 생성 | 매번 여기로 떨어짐 |

이걸 fallback 사다리(앞 단계가 실패하면 다음 단계로 떨어지는 안전망 구조)라고 부릅니다. 사다리 자체는 잘 짜여 있었습니다. 어떤 환경에서도 PNG(이미지를 무손실로 저장하는 파일 포맷) 한 장은 반드시 나옵니다. 문제는 1, 2단이 사실상 일하지 않아서 매번 3단계, 즉 단조로운 그라데이션과 ASCII 영문 박스가 출력되고 있었다는 점입니다.

3단 PIL 결과물에는 한 가지 더 약점이 있었습니다. PIL이 한글 폰트 렌더링을 제대로 처리하지 못해서, "OpenOrchestrator 시리즈 5편" 같은 한글 제목을 그림에 박으려면 영문자만 골라낸 뒤 빈 자리를 채우는 식으로 변환해야 했습니다. 결과적으로 글 제목의 의미가 그림에서 거의 사라졌습니다.

글 본문 품질이 올라갈수록 이 자동 썸네일이 글의 첫인상을 깎고 있다는 느낌이 점점 또렷해졌습니다.

1순위 자리에 새 단계 하나만 끼워 넣기

해결 방향은 단순하게 잡았습니다. 사다리 맨 위에 새 단계를 한 칸만 끼워 넣고, 아래 세 단계는 한 줄도 안 건드립니다.


0) LLM이 직접 그려주는 도구 (이번에 새로 추가, 1순위)
   ↓ 실패하면
1) 내부 이미지 API
   ↓ 실패하면
2) OpenAI 직접 호출
   ↓ 실패하면
3) PIL 그라데이션

원칙은 두 줄로 끝납니다.

- 새 경로가 잘 동작하면 기존 경로는 한 번도 호출되지 않습니다.

- 새 경로가 어떤 이유로든 실패하면 기존 경로가 아무 변경 없이 그대로 잡힙니다.

이번 변경은 "기존 사다리를 업그레이드"한 게 아니라 "위에 한 칸 덧붙이기"입니다. 기존 코드는 손대지 않으니 회귀(이전에 잘 동작하던 것이 새 변경으로 깨지는 현상) 위험이 거의 없습니다.

여기서 1순위로 둔 도구는 Codex CLI에 내장된 이미지 생성 기능입니다. 이미 ChatGPT Plus 구독 안에서 다른 작업에 쓰고 있던 도구라 별도 결제 경로를 새로 만들지 않아도 됐습니다.

비상정지 스위치 한 줄

새 경로가 망가져도 즉시 우회할 수 있도록, 환경변수(시스템에 저장되는 설정값) 한 줄로 새 경로를 강제로 끄는 스위치를 같이 만들었습니다.


OO_THUMB_NO_CODEX=1

이 변수가 1, true, yes 중 하나로 설정되면 새 경로는 시도조차 하지 않고 바로 1단계(기존 사다리)로 떨어집니다. 운영 중 이상 징후가 보이면 코드를 되돌리지 않고 환경변수만 바꾸면 됩니다.

이런 식의 작은 스위치는 자동화 시스템에서 의외로 자주 도움이 됩니다. 한 달쯤 지나서 "지난주 글 썸네일이 왜 안 좋게 나왔지?"라는 회고를 할 때, "그날만 이 변수가 1이었어요"라고 빠르게 원인을 좁힐 수 있기 때문입니다. 사고 후 디버깅 시간을 크게 줄여줍니다.

처음 돌렸을 때 만난 Windows 함정

새 경로를 처음 돌렸을 때 PNG 파일이 사용자가 지정한 경로에 안 만들어졌습니다. 토큰은 충분히 썼고, 도구는 호출됐는데, 결과물이 우리가 원한 자리에 도착하지 않은 채 끝나는 패턴이었습니다.

원인은 운영체제 환경에 있었습니다. 도구가 일하는 흐름이 두 단계로 나뉘어 있다는 걸 그제야 알게 됐습니다.


1단계: 도구가 PNG를 자기 캐시 폴더에 만든다
       (C:\Users\<사용자>\.codex\generated_images\<세션ID>\*.png)
2단계: 그 PNG를 사용자가 지정한 경로로 복사한다

1단계에서 PNG는 잘 만들어집니다. 문제는 2단계 — 이 복사 단계가 Windows의 PowerShell constrained language mode(PowerShell이 제한된 명령만 허용하는 보안 모드)와 충돌해 실패합니다.

도구 입장에서는 "복사가 실패했다"고 보고하지만, PNG는 캐시 폴더에 멀쩡히 살아 있습니다. 식당으로 비유하면 음식은 다 만들어졌는데 마지막 서빙 단계에서 트레이가 막혀 손님 자리에 못 갔다고 하는 것과 비슷합니다.

우회: 우리가 직접 가지러 가기

해결은 단순했습니다. 도구가 우리 자리에 PNG를 못 가져다 두면 우리가 직접 가지러 가면 됩니다.

흐름은 이렇게 잡았습니다.

1. 새 경로를 끝까지 돌리고, 우리가 지정한 저장 경로를 먼저 확인합니다.

2. 거기에 PNG가 있으면 그대로 씁니다 (도구가 정상 동작한 경우).

3. 없으면 도구의 출력에서 "세션 ID"를 찾아냅니다.

4. 그 ID에 해당하는 캐시 폴더로 가서 PNG를 찾고, 우리가 원래 원했던 경로로 직접 복사합니다.

5. 그래도 못 찾으면 "우리가 도구를 호출한 시각 이후에 새로 생긴 PNG"를 캐시 전체에서 찾습니다.

마지막 5번은 일종의 안전망입니다. 도구가 출력 형식을 미래에 바꿔도, "어쨌든 우리가 호출한 직후에 새로 생긴 PNG"라면 그게 우리 결과물일 가능성이 높습니다.

PNG를 우리 경로로 복사한 다음에는 옆에 작은 메타데이터 파일(어떤 도구로, 어떤 프롬프트로, 몇 초만에, 몇 바이트짜리 이미지를 만들었는지가 기록된 JSON)을 같이 만듭니다. 나중에 "이 썸네일은 어떤 글의 어떤 시도에서 나온 거지?" 같은 추적이 가능해집니다.

통합 후 어떤 일이 자동으로 일어나는가

이제 새 글을 발행할 때 흐름은 이렇게 됩니다.


글 초안 작성
  → 발행 파이프라인 실행
  → 대표이미지 자동 생성
      ├ 1순위: LLM이 직접 그려주는 도구
      └ 실패 시: 내부 API → OpenAI 직접 호출 → PIL 그라데이션
  → Tistory 비공개 임시저장
  → 사람 검토
  → 공개 발행

사람이 손대야 하는 자리는 이제 한 곳뿐입니다 — "비공개 임시저장된 글을 검토하고 공개 발행 버튼을 누르는" 단계. 대표이미지를 직접 고르거나 수정하는 단계는 일반적으로 사라집니다.

같은 제목으로 비교했을 때

새 경로와 기존 PIL 경로를 같은 글 제목으로 모두 돌려보고 결과물을 비교했습니다.

| 항목 | 이전 (PIL 그라데이션) | 이후 (LLM 직접 그림) |

|---|---|---|

| 파일 크기 | 약 250KB | 약 1.4MB |

| 가로 세로 | 1200x630 픽셀 | 1792x1024 픽셀 |

| 한글 제목 렌더링 | ASCII로 변환된 영문 박스 | 한글 그대로 정확히 표시 |

| 디자인 | 단조로운 그라데이션 + 텍스트 | 모던 인포그래픽 스타일 |

| 생성 시간 | 1초 미만 | 약 70초 |

| 회귀 시 즉시 우회 | 없음 | 환경변수 한 줄로 가능 |

생성 시간만 보면 70배 늘어났지만, 발행 사이클 전체로 보면 한 편당 1분 남짓의 차이입니다. 사람이 직접 썸네일을 만들거나 고르던 시간보다는 짧습니다.

의도적으로 손대지 않은 것들

이번 작업에서 의도적으로 건드리지 않은 부분도 있습니다.

- 비공개 임시저장 → 사람 검토 → 공개 발행이라는 발행 자체 흐름은 그대로 두었습니다. 검토 단계는 유지합니다.

- 영상이나 쇼츠 썸네일은 이번 변경 범위 밖입니다. 블로그 글 발행 경로만 다룹니다.

- 외부 결제 경로(API 키를 직접 호출하는 방식)를 새로 추가하지 않았습니다. 이미 사용 중인 도구의 내장 기능을 씁니다.

- 기존 fallback 사다리는 한 단도 제거하지 않았습니다. 새 경로가 실패할 때 즉시 회귀할 수 있어야 합니다.

이 "손대지 않은 것들"의 목록이 "바꾼 것들"만큼 중요하다고 생각합니다. 자동화 파이프라인은 한 번에 너무 많이 바꾸면 회귀 디버깅이 급격히 어려워집니다.

운영하면서 다시 확인한 것

이번 작업에서 다시 한 번 확인한 것은 세 가지입니다.

첫째, 외부 도구는 "생성"과 "배달"을 분리해서 봐야 합니다. 도구가 결과물을 만든 시점과 그 결과물이 우리가 원한 자리에 도착한 시점이 다를 수 있습니다. 그 사이에 운영체제 정책이 끼어들 여지가 있습니다.

둘째, 환경변수 한 줄짜리 비상정지 스위치는 거의 항상 가성비가 좋습니다. 코드 한두 줄 추가하는 비용 대비, 운영 중 사고가 났을 때 복구 시간을 크게 줄여줍니다.

셋째, 새 경로를 추가할 때는 "기존 경로를 어떤 조건에서도 깨뜨리지 않는다"는 제약을 먼저 잡고 시작하는 것이 결국 빠릅니다. 단계 순서만 바꿔도 fallback이 불완전해질 수 있습니다.

정리

블로그 자동 발행 파이프라인에서 마지막까지 어색하게 남아 있던 한 자리 — 대표이미지 — 를 정리했습니다.

방법은 새로운 1순위 경로(LLM이 직접 그려주는 도구) + 기존 fallback 사다리 + 환경변수 한 줄짜리 비상정지 스위치, 이 셋의 조합입니다. 새 경로는 한글 제목을 정확히 렌더하고, 디자인 품질이 한 단계 올라간 대표이미지를 만듭니다. 어떤 이유로든 실패하면 이전과 동일하게 동작합니다.

자동화의 끝은 "모든 것이 자동으로 됐다"가 아니라 "자동이 깨졌을 때 무엇으로 돌아가는지가 명확하다"에 가깝다고 다시 느낀 작업이었습니다.
